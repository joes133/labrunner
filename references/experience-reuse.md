---

## 0. 为什么单独冻结

经验复用是**附加模块**，不是核心流程。
核心是「真实执行 + 取证 + 填模板」，那部分已经能独立跑通。
经验复用解决的是「第二次跑同类实验能不能更快」，
属于优化项，不该拖慢第一个可用版本的交付。

---

## 1. 核心原则：存攻略，不存存档

| 能存 | 不能存 |
|---|---|
| 哪个版本装了会炸 | 可提交的代码正文 |
| 第 3 步会报什么错、为什么 | 运行结果 / 答案数据 |
| 这个实验实际耗时多少 | 报告正文段落 |
| 哪几步必须截图 | 填好的模板成品 |
| 老师看重报告哪部分 | 可直接交的 docx |

**存「怎么走」，不存「走到哪」。路还得他自己走。**

这条同时也是学术诚信边界：经验库不能变成作业答案库。

---

## 2. 经验四层

| 层 | 内容 | 敏感度 |
|---|---|---|
| L1 环境层 | 版本、依赖、装了会炸的组合 | 极高（换环境就失效） |
| L2 坑位层 | 症状 -> 原因 -> 修复 | 中（部分通用） |
| L3 节奏层 | 耗时、卡点、必截图点 | 个人化 |
| L4 画像层 | 老师看重什么、篇幅分布 | 中高 |

**L2 坑位层是金矿**：把「我踩过的坑」变成「你不用再踩」，
但每一步操作仍由执行者自己完成。

---

## 3. 三层匹配

仅靠「学校 + 实验题目」判定会误判，且误判代价大于漏判。

| 层 | 内容 | 作用 |
|---|---|---|
| L1 身份层（弱） | 学校 + 课程 + 实验名 | 只是候选，不足以判定 |
| L2 内容层（强） | 实验指纹 | 决定「是不是同一个实验」 |
| L3 环境层（适用） | OS + 工具链 + 运行方式 | 决定「经验能不能直接套」 |

### 指纹字段

```yaml
fingerprint:
  tools: [bochs, gcc, as86, ld86]      # 用到的命令 / 工具
  libs:  []                             # 用到的库
  steps: 6                              # 步骤数
  outputs: [截图, 可执行文件, 终端输出]   # 产出物类型
  section_titles_hash: a3f9c1           # 指导书章节标题结构
```

指纹从用户提供的资料中自动提取（阶段 1 体检时即可完成）。
比指纹相似度，不比名字——
这样「改名不换内容」能匹配上，「换名又换内容」会暴露。

### 匹配度分级

| 命中 | 匹配度 | 呈现 |
|---|---|---|
| L1 only | 低 | **不打扰**，安静跑完再说 |
| L1 + L2 | 高 | 弹三选一 + 摘要，让用户确认 |
| L1 + L2 + L3 | 极高 | 三选一，攻略默认可用 |
| L1 + L2，L3 不匹配 | 高但环境不同 | 只给流程/节奏经验，坑位标注「环境不同，仅供参考」 |

### 分层判定适用性

不同层对环境/身份的敏感度不同，不要一刀切：

| 层 | 跨环境能给吗 |
|---|---|
| 环境层 | ❌ 环境不同就别给 |
| 坑位层 | ⚠️ 给，但标注「可能不适用」 |
| 节奏层 | ⚠️ 只作参考区间 |
| 画像层 | ✅ 一般能给 |

## 4. 触发文案（已定稿，不要改措辞）

**匹配度 >= 60%**

```
检测到开发者仓库已内置相关实验
  重庆理工大学 / 网络安全 / AES 加解密
  初版 2026-03   复用 4 次   最近验证 2026-09
  环境 Win11 + Python 3.11   耗时参考 41min   步骤 6   坑位 4

  本次实验指纹匹配度 92%（高）

  这是你这次要做的实验吗？
  [是，用攻略]  [是，但我要裸跑]  [不是，忽略]
```

**匹配度 < 60%**

```
  本次实验指纹匹配度 41%（低）—— 内容似乎改版了

  仓库里的记录可能已不适用。
  [忽略，我从零跑]  [跑完后帮我重新采集一份]
```

**关键**：展示元信息摘要，不展示攻略内容。
用户才知道老师今年改没改题，模型不该替他拍板。

**裸跑模式跑完后自动附对照**（耗时对比 + 踩坑对比），
不占选项位，纯免费增值。

## 5. 复用计数代替时间衰减

**时间衰减是错的**，原因：
课程实验内容多年稳定、偶尔突变，时间不是有效信号。
用它当判据，结果就是所有老经验一律被降权——那复用就没意义了。

### 正确做法

```
confidence = f(指纹匹配度, 复用次数, 环境匹配度)
```

| 因子 | 判定 |
|---|---|
| 指纹匹配度（主） | >= 85% 高 / 60-85% 中 / < 60% 低 |
| 复用次数 | 0 次未验证 / 1 次单次 / >= 2 次稳定 |
| 环境匹配度 | OS + 工具链一致则高 |

**实时比对胜过时间推测。**
指纹对得上，五年前的记录也是高置信；对不上，昨天的记录也作废。

### 记录元数据

```yaml
recorded: 2026-03-14
last_verified: 2026-09-02
reuse_count: 4
source: verified-twice        # first-run 降权 / verified-twice 升 high
applicable_grades: [2024级, 2025级, 2026级]   # 可选，用户标注
```

每次跑完自动 `reuse_count + 1`、更新 `last_verified`。
**越用越可信，而不是越放越可疑。**

## 6. playbook 模板字段

借鉴运维 runbook 方法论（见文末「设计来源」）：

```yaml
---
id: netsec-aes
identity: { school: ..., course: ..., name: ... }
fingerprint: { tools: [...], steps: N, outputs: [...] }
env: { os: ..., toolchain: ... }
preconditions:            # 前置条件，不满足则中止，不要硬跑
  - Python 3.11
  - pycryptodome 已安装
estimated_time: 41min
owner: joes133
last_verified: 2026-09-02
reuse_count: 4
---

## 步骤
（每步：命令 / 预期结果 / 是否必须截图 / 耗时）

## 坑位
（症状 -> 原因 -> 修复）

## 回滚
环境搞脏后如何回到干净状态
（例：git checkout . && make clean）

## 报告结构
（各栏篇幅分布）
```

**三个不能漏的字段**（来自运维领域，我们最初设计遗漏了）：

1. **preconditions**：前置条件不满足就中止，别硬跑
2. **rollback**：实验环境搞脏后怎么恢复
3. **estimated_time**：时间参数，供下次预估用

## 7. 三次固化规则

> 运维原则：runbook 是临时脚手架，不是永久设施。
> 反复执行的步骤应该被自动化掉，而不是一直记在文档里。

**同一个坑踩到第 3 次 -> 把它固化成脚本**，而不是继续记在坑位库。

经验库的终点，是让一部分经验变得不必要。

## 8. 分层脱敏与贡献机制（愿景，未开发）

### 三层回流策略

| 层 | 位置 | 是否回流 |
|---|---|---|
| 通用坑位（按工具组织） | `references/known-issues/common/` | ✅ 公开 |
| 环境适配 / 脚本改进 | `scripts/` | ✅ 公开 |
| 课程经验（学校/老师/届数） | `.local/playbooks/` | ❌ 留本地 |

**仓库增值的主体应该是前两层（非竞争性贡献），不是课程经验（竞争性）。**
朋友贡献 Mac 适配、LaTeX 支持、脚本 bug fix —— 所有人受益。
他学校的 AES 实验第 3 步会报错 —— 只有同校同届有用。

### 一键贡献（未实现）

```
$ python scripts/contribute.py
扫描 .local/ ... 脱敏 ... 生成 contrib/<日期>-contrib.md
```

三级降级：
1. 检测到 gh 已装且登录 -> 一键 fork + PR
2. 没有 gh -> 生成 md 文件，用户发给作者
3. 最保底 -> 终端打印内容

**现实预期**：大部分人跑完作业就关电脑，贡献率不要抱期望。
真正让仓库变厚的还是作者自己。这个机制只是顺手埋的入口。

## 9. 冷启动路径

```
装好时 .local/ 为空
  -> 没有经验可匹配
  -> 第一次跑：安静执行，阶段 6 记账，阶段 8 复盘
  -> 跑完自动生成第一份 playbook 骨架
  -> 第二次跑同类实验才谈得上复用
```

**所以阶段 6 的记账（timeline.md + frictions.md）现在就必须做。**
它是经验库的采集端，现在不采集，未来启用时没有冷启动数据。

## 10. 设计来源

经验复用这件事，运维 / SRE 领域已经想了二十年，本模块直接借鉴其结论：

| 行业共识 | 本模块的对应 |
|---|---|
| Stale runbooks are worse than none | 印证「时间衰减是错的」，改用 last_verified + 内容比对 |
| Review and update after every use | 对应阶段 8 回写机制 |
| Include the why alongside the what | 对应坑位三元组「症状 -> 原因 -> 修复」 |
| Modular, not monolithic | 按实验拆小文件 |
| Automate before it becomes toil | 对应「三次固化规则」 |

可参考：Google SRE Book、Atlassian Incident Handbook、
NIST SP 800-61、GitHub 上的 community runbook 仓库。
